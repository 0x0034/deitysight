# 主机信息采集设计

本文记录设计讨论中已确认的需求与约束。最终技术设计已于 2026-09-18 确认，首版 agent 已实现；
实际验证范围见 [实施验证](../implementation-validation.md)。
领域术语见根目录 `CONTEXT.md`。

## 目标

已有监控指标提供主机负载情况与趋势。主机采集器补充详细信息，
将采集结果交给下一环节，用于分析相关进程与负载升高原因。

## 项目边界

本项目只实现 agent。交付内容包括 Linux 采集程序、配置与部署文件、
HTTP 任务接口、数据持久化与结果包，以及接口文档和调用示例。

server 是外部调用方，负责下发任务、获取结果，并在外部完成
Pod/业务归属补充及大模型分析；这些 server 能力不属于本项目实现范围。

## 已确认的约束

- 首版仅支持 Linux 主机。
- agent 使用 Go 实现，交付单一二进制，并通过 systemd 服务部署。
- agent 以 root 身份部署，仍须遵守只读采集、禁止进程控制及仅在指定存储目录写入采集数据的约束。
- 首版同时覆盖 CPU 争用、内存压力（含回收与换页）和 I/O 阻塞三个调查场景。
- 主机 agent 不调用大模型，仅采集、整理并向 server 回报足以支持调查的数据。
- agent 保留采集范围内的原始数据并打包，不以 Top N、排名或原因分析筛选输出；不要求在主机端先计算资源使用率或进行诊断。
- server 获取结果包后可以将其中的数据交给大模型分析；大模型调用仍属于 server 侧职责。
- server 接收采集结果并承担后续分析职责；具体分析方式及是否调用大模型不属于主机 agent 的职责。
- 仅进行资源预算内的状态读取与采样，允许采集本身产生受控开销。
- 禁止修改配置、控制进程，以及附加调试或动态探针。
- 只读约束针对被调查系统和进程；agent 可以在配置的存储目录内写入自身采集数据。
- 通过配置文件开关控制后台低频采样。
- 开关开启时进行后台低频采样。
- 开关开启时，收到请求仍执行本次窗口采样，返回近期历史与本次窗口采样结果；两部分分别标明时间范围。
- 开关关闭时不进行后台采样，等待请求到来后进行一个时间窗口的按需采样。
- 首版支持将进程关联到容器或 Kubernetes Pod。
- agent 回报宿主机进程身份、cgroup 路径，以及能够识别的容器 ID；server 补充容器、Pod 与业务归属。无法识别的归属明确标为未知。
- server 通过 HTTP 请求 agent 下发采集任务，agent 提供接收任务的 HTTP 接口。
- 接口采用 HTTP + token 认证，token 从 agent 配置文件读取；提交任务、查询状态和获取结果均需校验 token。沿用 Bearer Token 请求头传递方式。
- 按需采样默认窗口为 30 秒，默认步长为 5 秒；server 可以通过任务请求参数分别调整窗口和步长。
- HTTP 采集任务采用异步方式：提交后立即返回 `task_id`，server 通过 HTTP 查询任务状态并获取结果，不在提交请求中等待采样窗口结束。
- 每台主机同一时刻最多执行一个按需采集任务；执行期间拒绝新的采集任务并返回忙碌，不排队。已完成任务的结果仍可查询。
- 后台低频采样属于独立机制，不属于上述按需任务并发名额；其与按需采样的总开销仍须受资源预算约束。
- server 提交任务时提供 `request_id`。在 agent 保留对应任务记录期间，同一 ID 且参数相同的请求返回原 `task_id`，不启动新的采集；同一 ID 但参数不同则拒绝并报告冲突。
- 重复请求先按幂等规则处理；新 ID 才按单任务执行和忙碌拒绝规则处理。
- 数据存储目录通过 agent 配置文件指定，采集结果持久化为该目录中的文件。
- server 通过任务结果接口获取对应的结果文件，由 server 分析文件内容。
- agent 在按需采集中途重启后，将未完成任务标记为 `interrupted`，保留已落盘的部分结果并注明实际采集范围，不自动续采；server 可以获取这些部分结果进行分析。
- 结果保留时长、agent 数据存储容量上限和磁盘最小剩余空间通过配置文件控制。
- agent 自动清理自身已过期的数据；清理后空间仍不足时，停止新增采集并报告存储不足，不提前删除未过期的结果。
- 采集中途空间不足或写入失败时，停止当前任务后续采样并暂停后台采样，保留成功落盘的数据；能生成结果包则标为 `partial`，不能生成则标为 `failed`，记录原因。
- 空间恢复后不自动续采当前任务，重新调查需提交新任务；打包临时空间也计入存储预算，不得为了打包突破容量限制。

## 已确认的调查目标

| 场景 | 采集结果需要支持 server 调查的问题 |
| --- | --- |
| CPU 争用 | 哪些进程消耗 CPU，主机是否存在运行排队或 CPU 压力？ |
| 内存压力 | 哪些进程占用内存较多或增长明显，主机是否存在回收、换页或内存压力？ |
| I/O 阻塞 | 哪些进程产生 I/O 或处于阻塞状态，设备是否繁忙或存在等待？ |

采集范围、资源预算及数据源定义见后续章节与技术设计；实际可用性需在目标 Linux 环境验证。

## 已确认的完整采集范围

“完整”指以下资源调查范围内的完整采集，不按排名或 Top N 筛除进程。

| 范围 | 内容 |
| --- | --- |
| 主机 | CPU、内存、换页、运行队列、压力指标、磁盘 I/O |
| 全部可见进程与线程 | 身份、状态、CPU/内存/I/O 原始计数及等待信息 |
| 相关 cgroup | 归属路径、资源使用、限额与限流事件 |
| 采集元信息 | 实际采样时间、数据来源、主机启动标识、单位、读取错误及缺失项 |

- 不采集进程内存内容、环境变量或业务文件正文。
- 保留原始数据；结果包仍须提供识别和解释这些数据所需的采集元信息。
- 权限不足、进程退出或预算限制导致无法完整采集时，明确标记缺失或不完整，不能将读取失败当作指标为零。

## 已确认的配置默认值

以下默认值均允许通过 agent 配置文件调整。

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 后台采样开关 | 关闭 | 关闭时仅按请求进行窗口采样 |
| 后台采样步长 | 30 秒 | 后台采样开启时生效 |
| 后台历史保留范围 | 最近 10 分钟 | 用于向任务提供近期观测记录 |
| 任务结果保留时长 | 任务结束后 24 小时 | 中断任务同样适用 |
| 任务元数据与幂等记录保留时长 | 任务结束后 7 天 | 与结果文件保留时长独立配置 |
| agent 数据存储容量上限 | 1 GiB | 限制 agent 自身持久化数据占用 |
| 磁盘最小剩余空间 | 1 GiB | 空间不足时按已确认的清理与停止新增采集策略处理 |
| 按需采样窗口 | 30 秒 | server 可通过任务请求参数覆盖 |
| 按需采样步长 | 5 秒 | server 可通过任务请求参数覆盖 |
| 最大按需采样窗口 | 300 秒 | 请求不得超过 agent 配置的上限 |
| 最小按需采样步长 | 1 秒 | 请求不得低于 agent 配置的下限 |
| 单任务最多计划采样点 | 301 个 | 包含起始基线和结束采样 |

默认值是初始配置，实际采集开销需在实现后测量。

## 已确认的采样参数校验

- 采样步长不得大于采样窗口。
- 请求必须同时满足最大窗口、最小步长及最多计划采样点的限制。
- 超出限制时拒绝请求并说明原因，不静默修改请求参数。
- 参数限制由 agent 配置文件控制，server 只能在这些限制内调整任务参数。

## 已确认的部署资源限制

| 资源 | systemd 初始限制 |
| --- | --- |
| CPU 配额 | 单核的 20%，即 0.2 核 |
| 内存硬上限 | 256 MiB |

- 上述限制通过 systemd 部署配置调整，不由 agent 修改自身的系统资源控制配置。
- 数值是待实测验证的初始值；CPU 配额不足导致的采样缺失须如实记录。
- 达到内存硬上限可能导致 agent 被终止；重启后按 `interrupted` 规则恢复未完成任务记录，不自动续采。

## 已确认的采样调度规则

- 以任务实际采样开始时间为基准，按固定时间点启动各轮采样。默认 30 秒窗口、5 秒步长的计划时间点为第 0、5、10、15、20、25、30 秒。
- 窗口不能被步长整除时，额外安排窗口结束时的采样；例如 12 秒窗口、5 秒步长对应第 0、5、10、12 秒。
- 上一轮尚未结束而错过下一采样点时记录缺失，不并发补采，也不延长窗口。
- 后台采样与按需任务共用串行采样执行器；同时到期时优先任务采样，同一次采样结果可复用于后台历史。
- 每轮记录实际起止时间，不将整轮数据描述为同一瞬间的快照。

## 已确认的结果包格式

任务结果以 `tar.gz` 压缩包交付，内容如下：

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | 任务参数、实际时间范围、完整性及格式版本 |
| `samples.jsonl` | 本次采样的逐条原始记录，包含来源、时间与原始内容 |
| `history.jsonl` | 后台采样开启时提供的近期历史记录 |
| `errors.jsonl` | 读取失败、缺失项及原因 |

JSONL 用于保存原始记录，不代表主机端进行了排名或诊断。
server 下载并解包后，读取其中的文本交给大模型分析。

## 已确认的任务状态与交付规则

| 状态 | 含义 |
| --- | --- |
| `running` | 正在采集或打包 |
| `completed` | 采样完成，约定范围内数据完整 |
| `partial` | 有可用结果，但部分读取失败、采样缺失或受预算限制 |
| `failed` | 无可用采集数据，或无法生成结果包 |
| `interrupted` | agent 重启导致任务中断，不自动续采 |

- 部分数据读取失败时继续采集其他项目，将成功数据和失败原因一起打包。
- 结果包生成完成后才开放下载，避免 server 读到正在写入的文件。
- 中断任务也可下载成功恢复并打包的部分结果。
- 任务状态与是否存在可下载结果包分别表达；标记为 `interrupted` 不代表结果包已经可用。

## 已确认的任务记录保留与过期规则

- 任务元数据与 `request_id → task_id` 映射一起持久化，默认从任务结束起保留 7 天，可通过配置调整。
- 结果文件按独立配置保留，默认从任务结束起保留 24 小时。
- 结果文件过期后，任务记录仍在时允许查询原任务状态；下载接口明确返回结果已过期。
- 幂等记录仍在时，相同 ID 且参数相同的重试请求返回原任务，不因为结果已过期而重新采集；同一 ID 但参数不同仍按冲突处理。
- 需要重新采集时，server 使用新的 `request_id`。

## 已知限制

- HTTP 不加密传输，token 与采集数据在传输链路上为明文。
- 关闭后台采样时，无法靠请求之后的采样还原已经消失的进程现场。
- 开启低频采样也不能保证捕获短于采样间隔的进程。
- 采集结果是分析证据，不等于已确认的根因。
- D 状态任务不一定在等待本地磁盘，不能仅凭任务状态断言磁盘故障。
