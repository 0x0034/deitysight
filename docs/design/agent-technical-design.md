# Agent 技术设计

本文件将 [已确认需求](host-collection.md) 转成可实现的接口与存储设计。
设计已于 2026-09-18 经用户整体确认，作为后续实现依据。
本文件补充的字段、路径、超时和恢复细节均已确认；性能与 Linux 兼容性仍须通过实现验证。
首版代码、配置、服务模板与验证用例已实现。实际测试证据与尚未验证的范围见
[实施验证](../implementation-validation.md)。

## 1. 交付与模块职责

- 一个 Linux Go 二进制，使用标准库 HTTP 服务；除配置启用的白名单 atop 固定调用外，不执行 shell 或其他外部命令。
- 支持 Linux amd64、arm64；按运行环境检测 cgroup v1/v2 和可选内核数据源。
- 交付 agent、YAML 配置示例、systemd 服务模板、HTTP 与结果协议文档、验证用例和调用示例。
- 配置与 API 层只接受固定任务参数，不接受命令、任意采集路径或任意下载路径。
- 任务管理器拥有单任务并发名额、幂等校验、任务生命周期和状态持久化。
- 采样器负责白名单数据源、固定调度、原始记录及缺失记录；不负责归因或排名。
- 存储模块统一负责任务文件、后台历史、配额、恢复、打包及过期清理。
- server 为外部调用方。本项目不实现 Kubernetes API 查询、业务归属数据库或模型调用。

## 2. 配置

命令行通过 `--config` 指定配置文件；配置在启动时加载，首版不做热更新。
配置文件必须由管理员部署，root 可读；示例 token 是占位符，不能用于实际启动。
HTTP 监听默认仅本机，部署时明确改为 server 可达的管理网地址。

```yaml
http:
  listen: "127.0.0.1:19100"
  token: "REPLACE_WITH_DEPLOYMENT_SECRET"
storage:
  path: "/var/lib/deitysight"
  result_retention: "24h"
  task_retention: "168h"
  max_bytes: 1073741824
  min_free_bytes: 1073741824
background:
  enabled: false
  step: "30s"
  retention: "10m"
sampling:
  default_window: "30s"
  default_step: "5s"
  max_window: "300s"
  min_step: "1s"
  max_points: 301
  round_timeout: "2s"
  max_source_bytes: 1048576
```

已确认的 systemd 配额为 `CPUQuota=20%`、`MemoryMax=256M`，由部署配置管理，
不由 agent 通过写入系统 cgroup 来调整。`round_timeout` 与 `max_source_bytes`
采用上述已确认的初始值，需以完整性与开销实测验证。

配置校验：路径必须是本地绝对路径且不可是 `/` 等宽泛目录；存储目录由 agent 专用，
目录权限 `0700`、文件 `0600`。token 非空且不能为示例占位符；时长和容量必须为正，
默认采样参数必须满足限制，任务记录保留时长不得短于结果保留时长。
配置文件及其 token 不进入结果包或日志。

## 3. HTTP 协议

所有下列接口均校验 `Authorization: Bearer <token>`，不把 token 放进 URL。
HTTP 不提供传输加密，这一点沿用已确认决策。

| 接口 | 行为 |
| --- | --- |
| `POST /v1/tasks` | 接收任务，持久化记录后返回 `task_id` |
| `GET /v1/tasks/{task_id}` | 查询状态、进度、缺失摘要、结果是否可用 |
| `GET /v1/tasks/{task_id}/result` | 流式下载已发布的 `tar.gz` 文件 |
| `GET /v1/health` | 查询恢复状态、存储可用性与采样器是否可接受任务 |

首版不提供远程执行命令、任务取消、删除任务或修改配置的接口。

请求示例（窗口与步长为可省略的正整数秒）：

```json
{"request_id":"investigation-0001","window_seconds":30,"step_seconds":5}
```

新任务返回 `202 Accepted` 和 `Location` 状态查询路径。
相同 ID 的幂等重放返回 `200 OK`、原 `task_id` 和 `reused: true`。
用户提供的 `request_id` 仅存入元数据，不作为目录名；目录使用 agent 生成的 UUID。
请求正文上限为 8 KiB，request_id 为 1–128 字节的非空 UTF-8 字符串；
拒绝未知字段、重复 JSON 键、多个 JSON 对象及非整数的时间参数。
时间参数省略才使用默认值，显式的零、负数和 null 均视为无效。

幂等参数比较使用规范化后的有效参数：省略值在首次提交时展开并持久化。
重放时省略的参数沿用该任务首次提交的值，不受 agent 重启后默认配置变化影响；
显式传入的不同值仍视为冲突。幂等记录有效时，参数一致的重放优先于忙碌、存储不足等新任务准入检查。

| 情况 | HTTP 状态与错误码 |
| --- | --- |
| token 无效或缺失 | `401 unauthorized` |
| 参数格式、范围或字段不合法 | `400 invalid_request` |
| 请求正文超过上限 | `413 request_too_large` |
| 同一 request_id、参数不同 | `409 request_conflict` |
| 已有按需任务，收到新任务 | `409 agent_busy` |
| 任务存在但结果尚未可用或无法生成 | `409 result_not_ready` / `409 result_unavailable` |
| 已知任务的结果已过期 | `410 result_expired` |
| task_id 不存在或任务记录已过期 | `404 task_not_found` |
| agent 存储预算不足或不可写 | `507 storage_unavailable` |
| 正在启动恢复或采样器无法继续执行 | `503 agent_unavailable` |

错误正文统一为 `{"error":{"code":"...","message":"..."}}`。
结果下载中断不删除文件，server 可以在保留期限内重试。
返回 `Content-Length` 和基于归档 SHA-256 的 `ETag`；不会在每次下载时重新打包。
下载不延长结果或幂等记录的保留时间。

状态响应区分任务结局与结果可用性，例如：

```json
{
  "task_id": "<uuid>",
  "request_id": "investigation-0001",
  "state": "partial",
  "phase": "finished",
  "window_seconds": 30,
  "step_seconds": 5,
  "planned_points": 7,
  "sampled_points": 6,
  "missed_points": 1,
  "result": {
    "available": true,
    "expired": false,
    "url": "/v1/tasks/<uuid>/result"
  },
  "errors": [{"code":"sample_missed","count":1}]
}
```

实际响应还包含请求接收、采样开始、最后采样结束、任务结束及各项过期时间；
未发生的时间为 `null`，不能用零时间或虚构时间替代。
`running` 的 phase 区分 `sampling` 与 `packaging`；不新增对外任务状态。

## 4. 调度、截止时间与完整性

任务的采样基准 `t0` 是执行器实际启动首轮的时间，而非 HTTP 接收时间；两者均记录。
已有后台扫描可以完成或触及截止期限后让出执行器，不为新任务再创建一个并行扫描器。
同一时刻只有一个按需任务，从接收、采集到打包完成都持有任务名额。
执行器因先前读取受阻而不可用时拒绝新的采集任务，不以 running 名义无限积压任务。

计划采样点为 `0, step, 2*step, ...` 加唯一的窗口结束点。
计划点数为 `ceil(window/step) + 1`，使用无溢出的整数运算预先校验。
计时使用单调时钟；对外同时保留 UTC 时间、相对偏移和实际起止时间。

每轮软时间预算为 `min(round_timeout, step)`；默认参数下为 2 秒。
到期后不再启动新的数据源读取，已取得的数据保留，未读取部分记为缺失。
不承诺能够强制打断阻塞中的内核读取，也不因超时不断创建新读取线程。
未返回的读取仍占用串行执行器；新采样点按缺失处理，并由健康接口报告采样器受阻。

“不延长窗口”指不增加或补发计划采样点；窗口末端启动的最后一轮读取及其后的打包
仍需有限处理时间。因此 30 秒窗口的任务不承诺在第 30 秒结果就可下载。
资源限制下实际超时或调度延迟必须记录，不能将计划时间冒充读取时间。

后台按自己的固定时间表调度。与任务点重合且采集范围一致时复用原始记录，
否则执行器忙碌导致的后台缺点单独记录，不在事后密集补采。

单个数据源超过 `max_source_bytes` 时保留已读部分并标记截断，不能将其视为完整记录；
不按 CPU 或内存排名裁剪进程。遍历范围、成功数、失败数和因预算未访问的对象须可区分。

任何约定范围内的实际数据缺失使任务为 `partial`，包括不支持的数据源、权限不足、
进程读取期间退出、超时或截断；若没有可用采集数据或无法生成结果包，则为 `failed`。
按内核接口定义不适用的字段单独声明 `not_applicable`，例如某些根 cgroup 不提供的限额文件、
当前使用 v1 时的 v2 专属文件；不将这些情况当作读取失败。预期可读但实际未取得的数据仍为缺失。
用户关闭后台采样不是缺失。后台刚启用、历史尚不足 10 分钟时标明实际覆盖范围和原因，
不能宣称拥有完整 10 分钟历史；实际历史采样错误仍计为缺失。

## 5. 原始记录与结果包

沿用已确认的四类结果文件。`samples.jsonl` 与 `history.jsonl` 使用相同记录结构，
每条记录至少包含：格式版本、sample_id、source、实际读取起止时间、相对时间、
对象身份、content_encoding、原始内容与完整性标记。
文本中已有的单位保持原样；单位不自明的字段通过 manifest 的数据源说明解释。
非 UTF-8 内容使用 Base64 并明确编码，不无提示地替换原始字节。
数据源说明须标明计数作用域和共享关系：进程级聚合值不能再次与线程值相加，
同一地址空间的线程内存字段不能视为各线程独占内存；I/O 的系统调用字节数和存储字节数分别解释。
`wchan` 原始值为 0 时保留该值及可见性限制，不能推导为没有等待或已证明读取成功。

进程身份使用主机身份、boot_id、PID 与启动计数共同识别，线程额外包含 TID 与线程启动计数。
单靠 PID 或进程名不能识别跨采样的同一个对象。
读取身份前后发现对象已退出或 PID 被复用时标记身份不稳定，不把两代对象拼接成一份记录。

manifest 至少包含：

- agent 与 schema 版本、主机身份、内核版本、架构、boot_id、CPU 数、时钟节拍和页大小。
- task_id、request_id、有效采样参数、实际时间覆盖、计划及实际采样点数。
- 后台采样是否开启、历史覆盖范围、支持和缺失的数据源、记录完整性摘要。
- 结果文件清单及各数据文件的长度和 SHA-256；不包含 token 或完整 agent 配置。

主机身份元信息区分持久化的 agent_id、主机名与 boot_id；agent_id 首次启动时生成并保存于 identity.json。
这些标识用于证据关联，不冒充外部 server 的资产 ID 或 Kubernetes 节点身份。

采样原文与元信息都以流式方式写入和读取，不把全部窗口数据放入内存。
agent 对 PID/cgroup 路径的解析只用于标识、定位和完整性校验，不用于业务诊断。

## 6. 落盘与幂等恢复

使用文件存储，不额外引入数据库进程。目录结构示例：

```text
<storage.path>/
  agent.lock
  identity.json
  tasks/<task_id>/
    task.json
    samples.jsonl
    history.jsonl
    errors.jsonl
    result.tar.gz
  background/<sample_id>.jsonl
```

一个存储目录只能由一个 agent 实例持有独占锁，防止多实例破坏单任务约束。
task.json 保存 request_id、规范化参数、状态、时间与文件元信息，是恢复任务与幂等索引的权威记录。
内存索引从这些记录重建，不维护一个必须与 task.json 跨文件原子同步的持久化映射。
任务元数据损坏、重复 request_id 指向不同任务或恢复存在冲突时，报告恢复异常并暂停新任务准入；
不能跳过坏记录后将同一 request_id 误判为全新请求。仍可提供可验证的既有任务查询和下载。

新任务先创建并同步任务记录和目录，再确认接收、开始采样。
task.json 更新采用同目录临时文件、同步、原子替换及目录同步；失败不得返回虚假接收成功。
进程崩溃前未获得成功响应的请求，若已有完整任务记录，重试仍按该记录幂等处理。

JSONL 在每轮结束时同步，恢复时保留所有可解析的完整记录。
不完整尾行明确记入恢复错误；中间损坏不能当作无损恢复，保留原始损坏文件以供排查。
“已持久化”不承诺保存崩溃前仍在内核或程序缓存中、尚未成功同步的数据。

归档先写临时文件，完成校验和同步后原子发布，再持久化终态及结果元信息。
只有终态记录已提交且归档可验证时允许下载。
若重启时任务记录仍为 running，即使临时或候选归档存在，也按 interrupted 恢复，
从已落盘记录重新生成带中断信息的结果包，不把未提交的候选包当作已完成结果。
打包恢复不等于恢复采样，绝不补采原任务。

已终结任务保持原状态；文件损坏或丢失时，将结果可用性标为异常并报告原因，不重新采集。
interrupted 任务的结束时间以启动恢复确认中断的时刻记账，实际最后采样时间单独保存；
24 小时结果保留和 7 天元数据保留从这个结束时间起算，后续重启不重复刷新。
重启期间恢复未完成时拒绝新任务，避免与恢复打包争用存储和执行名额。

## 7. 后台历史与清理

后台每轮采用独立文件原子发布，按该轮实际结束时间保留最近 10 分钟，并持久化缺失记录。
任务首轮开始时冻结当时可用的近期历史范围，固定复制到任务自己的 history.jsonl；
后续后台清理不影响已接受任务的结果。复制和任务采样交错时，任务采样优先，复制读取固定的已完成历史文件。
被任务引用且尚未复制完的历史文件暂不清理，所占空间始终计入总预算。

存储预算包含元数据、后台历史、任务原始数据、损坏保留文件、临时文件和归档，不能只统计最终 tar.gz。
写入和打包均检查 agent 预算与所在文件系统的剩余空间；同时预留元数据收尾和打包空间。
估算不能代替实际写入限额，流式打包也要执行预算检查。

按已确认规则处理运行中空间不足或写入错误：停止后续采样、暂停后台、保留已落盘数据，
可打包则 partial，否则 failed。磁盘完全不可写时不能承诺状态立即持久化，
内存状态与日志报告存储错误；重启后仍以已持久化记录和 interrupted 规则恢复。
健康恢复后后台按正常时间表自动恢复，新任务可再次提交，旧任务不续采。

清理周期为 60 秒，逻辑过期在每次访问时检查，不能因为定时清理尚未执行而继续提供已过期结果。
运行中任务不按 TTL 清理；已建立的下载流持有文件引用直至结束，过期后拒绝新的下载。
未释放空间仍计入预算，不为绕过容量限制而强删未过期任务。
结果过期删除结果及其原始采样附件，保留任务与幂等记录；记录到期后幂等保证结束，未知旧 request_id 无法与全新 ID 区分。
即使元数据文件尚未被定时清理，超过逻辑保留期限后也不再作为有效幂等记录；
过期检查与接收新任务的判断须串行化，不能让同一 request_id 同时存在两个有效任务。

## 8. Linux 数据源与部署约束

详细白名单及接口限制见 [Linux 数据源核查](linux-data-sources.md)。
agent 只读内核公开状态与计数接口，不递归打包整个 /proc、/sys 或业务目录。
沿用已确认范围，不采集进程内存内容、环境变量或业务文件正文，不执行 shell、任意外部命令或动态探针；可选 atop 仅使用固定路径和 `-P ALL <interval> 1` 参数，并将原始输出作为辅助记录。
首版不采集命令行参数，进程识别使用进程名、身份与 cgroup。
配置的存储目录之外不由 agent 创建或修改文件；运行日志输出到 stderr，由 systemd 收集。

systemd 模板需保护文件系统、配置与内核控制入口，只开放专用存储目录写入。
root 与 capability 设置本身不构成完整的只读保证；可见性和禁止写入/进程控制必须在 Linux 集成环境验证。
不能为了沙箱而无提示地隐藏其他用户或宿主机进程；缺失必须如实输出。
对 PID 复用、proc 魔术链接、cgroup 路径与符号链接做受限解析，拒绝越出白名单数据源或专用存储目录。

## 9. 验收依据

- 默认请求产生 7 个计划采样点；非整除窗口、超时、重叠与丢点遵守固定时序。
- 并发新任务只有一个被接受；相同 request_id 重试复用，参数冲突拒绝，重启后仍成立。
- 覆盖 CPU、内存、I/O 原始记录、线程及 cgroup 数据；验证不误加共享计数和不拼接复用 PID。
- 保留读取失败、权限限制、不支持、截断及实际时间；不能把缺失输出为零。
- 完成、部分、中断、失败、过期任务均具有一致的状态与下载行为。
- 在元数据写入、JSONL 写入、归档发布各阶段注入崩溃，检验恢复和文件完整性。
- 验证磁盘预算包含临时文件；ENOSPC、只读存储及清理下载竞态不破坏未过期结果。
- 在 Linux 上验证两种 cgroup 模式和实际 systemd 单元的数据可见性及写入限制。
- 大进程/线程数量下测量 CPU、RSS、每轮延迟、缺失比例与包大小，验证 0.2 核和 256 MiB 配额下的实际覆盖率。
- 不将这些尚未执行的验收项描述为测试已通过。
